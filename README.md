# HomeLedger

[![CI](https://github.com/khantroll/HomeLedger/actions/workflows/ci.yml/badge.svg)](https://github.com/khantroll/HomeLedger/actions/workflows/ci.yml)

HomeLedger is a privacy-first, local household finance desktop application inspired by the workflows of classic desktop finance software.

## Current status

Milestone 2 transaction-register slice plus the core Milestone 3 planning workflow. The React interface, restricted Tauri command boundary, versioned SQLite schema, durable transaction creation/editing/deletion, ordered split editing, atomic linked-account transfers, account statement reconciliation, local CSV/TSV/OFX/QFX/QIF import, deterministic merchant rules, and encrypted backup/restore are implemented. The Bills view manages scheduled expenses, income, and same-currency account transfers with weekly, biweekly, semimonthly, monthly, annual, and custom recurrence; shows recent and upcoming occurrences; and supports explicit posting, skipping, and linking ordinary transactions to existing ledger entries. Recurring transfers post as a balanced linked pair. Each schedule can opt into a reviewed auto-post queue: HomeLedger shows the exact due and overdue items, requires confirmation, revalidates them, and posts the complete batch atomically. Bills also detects stable weekly, biweekly, monthly, and annual expenses from local history, explains the cadence and amount evidence, suppresses existing schedules, and requires review in the normal editor before creating anything. Statement review offers conservative scheduled-occurrence candidates after merchant rules, explains its evidence, requires an explicit choice, and atomically links an approved match with its imported transaction. The Budget view supports monthly category allocations, actual spending, month navigation, optional rollover for sinking funds, and account-linked savings goals with target dates and monthly contribution plans. Goal progress comes from the real balance of one dedicated savings account, with deterministic required-monthly, projected-completion, and on-track status calculations. Forecast combines current liquid balances, expected scheduled activity, remaining monthly plans, and recurring transfers that cross the selected cash-account boundary into local 30/60/90/180/365-day expected, conservative, and optimistic projections. Transfers entirely within that boundary are cash-flow neutral. The Debt view stores currency-scoped payoff settings for credit-card and loan accounts, compares snowball, avalanche, and custom ordering, and shows deterministic payoff dates, total interest, payoff order, and balance checkpoints without posting transactions. Reports provide currency-safe income, spending, net cash flow, savings-rate, monthly-trend, category, and payee views with date/account filters and transaction-level drill-down. Split categories replace their parent category in spending totals, while transfers and reconciliation adjustments are excluded. Overview shows a concise projection from the same occurrence data. Pausing or skipping does not change the recurrence anchor, and deleting a template retains terminal occurrence provenance. Reconciliation matches selected transactions against opening and closing statement balances, requires an exact zero difference, retains statement history, and protects completed items from later edits, deletion, or batch undo. A linked transfer creates balanced withdrawal/deposit records, keeps both sides synchronized during edits, and deletes both sides in one database transaction. Imported QIF splits can be reviewed and edited, while direct deletion of imported rows is blocked to preserve complete-batch audit and undo guarantees. Imports also support reusable account-specific CSV/TSV mapping profiles, UTF-8/UTF-16/Windows-1252 decoding, comma/tab/semicolon delimiters, explicit date and decimal conventions, provider transaction IDs, exact/probable/possible duplicate review, currency checks, rule-based payee cleanup and categorization, and atomic commits. Browser development uses synthetic in-memory records; the native Tauri application uses its private local SQLite database. Investment-account OFX/QIF, import redo, live-database encryption, and AI integrations are not yet implemented.

## Development

Requirements for the web interface: Node.js 20 or newer.

```sh
npm install
npm run dev
npm test
npm run build
```

Native desktop development also requires the Tauri 2 prerequisites, Rust, and platform webview/build tools. On Windows, install the Microsoft C++ Build Tools and WebView2 as described by Tauri, then run:

```sh
npm run tauri dev
```

Every push to a development branch and every pull request runs the browser tests and production web build on Linux. CI also treats Rust Clippy warnings as errors, runs the native tests, and compiles the Windows desktop application without creating an installer bundle.

## Privacy posture

The current milestone makes no network calls and contains no real financial data. Native records are stored in `homeledger.db` under the operating system's application-data directory. The live SQLite database is not yet encrypted, so use only test data on untrusted or shared devices.

Encrypted `.hlb` backups use AES-256-GCM with authenticated metadata and a PBKDF2-SHA-256 password-derived key. The password is never written to disk or sent to a service, and there is no password recovery. Restore validates authenticated encryption, the SQLite header and integrity check, supported schema version, required tables, and foreign-key relationships before replacing the ledger. A temporary rollback snapshot is used if replacement fails and is removed when the operation completes.

CSV, TSV, OFX, QFX, and QIF files are parsed in application memory. The original file is not copied into the database; only approved normalized transaction fields, categories and splits when supplied, provider transaction ID when supplied, and the source filename are retained. OFX/QFX support covers bank and credit-card statements. QIF support covers bank, cash, and credit-card transactions; QIF does not carry a currency, so amounts use the selected local account's currency. Investment transactions are rejected explicitly rather than misinterpreted.

Merchant rules are local, deterministic, and evaluated by priority. They can match normalized payee text exactly, by prefix, or by containment; optionally scope themselves to expenses or income; and rename or categorize matching imports. An explicit source category or split allocation always wins over a rule. HomeLedger stores the original payee alongside a rule-renamed payee for auditability, and the native import command reapplies the rules inside the same database transaction instead of trusting browser preview data.

Undo deletes every transaction still belonging to the selected import batch in one SQLite transaction and then marks the retained batch record as undone. If the batch transaction count no longer matches its original audit value, HomeLedger refuses the undo rather than partially deleting it.

Delimited import profiles are matched by their normalized header layout and can remember the destination account, column mapping, date order, and decimal convention. Text is decoded locally with strict UTF-8 validation, UTF-16 detection, and a Windows-1252 fallback. Duplicate review is deterministic: provider IDs or identical date/amount/description combinations are exact and excluded; same-date/amount or strongly similar nearby transactions are probable; same-amount transactions within three days are possible. Probable and possible matches are skipped by default but can be explicitly included during review. Scheduled matching is a separate local review step and never weakens duplicate detection: it considers only active, unlinked occurrences for the selected account and direction, scores normalized payee, date, and amount evidence, and never links without an explicit choice. The native command recalculates eligibility and commits the imported transaction and occurrence link in one SQLite transaction. Budget totals are also deterministic and local: ordinary expense transactions count once, split lines replace their parent category for calculation, transfers are excluded, and rollover starts with the first saved allocation for that category.

Cash-flow forecasts are calculated locally and never post ledger transactions. Expected uses entered scheduled amounts and remaining monthly plans. Conservative assumes 10% less scheduled income and 10% more scheduled and planned spending; optimistic assumes 5% more scheduled income, 5% less scheduled spending, and 10% less planned spending. Scheduled expenses are deducted from matching budget categories before the remaining plan is spread through the month, preventing double counting. Accumulated rollover is reserved cash rather than assumed spending. Only checking, savings, and cash balances in the selected currency are included. A recurring transfer between included cash accounts is neutral; one crossing that account boundary is represented as an exact inflow or outflow.

Transaction reports are calculated locally from the selected currency and account scope. Expense reports use split lines in place of their parent category, preserve exact contributing transaction IDs for drill-down, and exclude linked transfers and reconciliation adjustments. Pending transactions remain included so report totals match the current ledger rather than silently forecasting their removal.

Debt payoff projections are calculated locally in integer minor units. They assume fixed APRs and fixed entered minimum payments, add interest monthly with nearest-cent rounding, roll freed minimum payments into the selected strategy, and stop after 1,200 months if the plan does not amortize. Snowball targets the smallest current balance, avalanche targets the highest APR, and custom uses the saved priority order. Plans are isolated by currency and never create ledger transactions.

Subscription detection is deterministic and local. It considers cleared, pending, or reconciled expenses from the most recent three years, requires at least three payments, rejects inconsistent cadence or amounts, ignores transfers, adjustments, and review items, and suppresses merchants already represented by a schedule. A candidate only prefills the ordinary schedule editor; the user must review and save it explicitly.

Savings goals are deterministic and local. Each goal is attached to one active savings account, and each savings account can back only one goal so progress is not silently counted twice. The current account balance determines funded progress; the target and planned monthly contribution determine the required monthly amount, projected completion month, and complete, on-track, at-risk, or overdue state. Goal planning never creates transactions or moves money.
